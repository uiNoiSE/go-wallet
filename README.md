# Go Wallet Service


[🇬🇧 README on english](https://github.com/uiNoiSE/go-wallet/blob/main/README.en.md)

Высококонкурентный, отказоустойчивый REST-сервис для управления кошельками, разработанный для работы в условиях экстремальных нагрузок с жесткими гарантиями консистентности. Спроектирован с упором на скорость записи и целостность данных, достигая производительности в 3600+ RPS на один кошелек без дедлоков в БД и race conditions.

### 🚀 Архитектурные решения (Почему Append-Only?)
Главным требованием ТЗ была обработка высокой конкурентной нагрузки (1000+ RPS на один кошелек) без потери запросов (ошибок 50X) и искажения баланса.

#### Проблема наивных подходов
Обычно для обновления баланса разработчики используют блокировку строк на уровне БД через `SELECT FOR UPDATE`. Под высокой конкурентной нагрузкой на один и тот же кошелек это неизбежно приводит к:
1. **Дедлокам в СУБД:** Потоки взаимно блокируют друг друга в ожидании освобождения строки;
2. **Просадке производительности:** Запросы выстраиваются в очередь, пул соединений исчерпывается, и клиент получает 504 Gateway Timeout.

#### Решение: Журнал транзакций (Append-Only Ledger / Event Sourcing на минималках)
Вместо изменения одной и той же строки баланса «на месте» (in-place mutation), данный сервис обрабатывает базу данных как **неизменяемый лог операций**.
* **Депозиты и Списания:** Каждый запрос — это чистый `INSERT` в таблицу `transactions`. Операции вставки не блокируют существующие строки, позволяя PostgreSQL выполнять их параллельно на максимальной скорости дисковой подсистемы.
* **Расчет баланса:** Текущий баланс рассчитывается динамически через оптимизированную агрегацию (`SUM(amount)`).
* **Защита от овердрафта (Проверки «на лету»):** Для списаний сервис выполняет быструю проверку на основе текущего состояния изоляции транзакций. При попытке параллельного double-spending данные остаются консистентными, так как средства невозможно списать из незакоммиченного состояния лога.

Эта парадигма перенесла узкое боттлнек системы со сложных синхронных блокировок строк на сверхбыструю параллельную запись в БД.

### 📊 Нагрузочное тестирование

Система была протестирована под высокой конкурентной нагрузкой, симулирующей состояние гонки для одного аккаунта.

#### Concurrent Test Results:
* **Всего запросов:** 500 параллельных транзакций
* **Время выполнения:** ~138.6 мс
* **Пропускная способность (RPS):** **~3607 запр/сек**
* **Целостность данных:** 100%. Финальный баланс сошелся копейка в копейку. Ноль упавших запросов, ноль ошибок 50X.

### 🛠️ Стек технологий

* **Язык разработки:** Go (1.26)
* **База данных:** PostgreSQL (18)
* **Миграции Tool:** Goose
* **Контейнеризация:** Docker / Docker Compose

### ⚡ Быстрый запуск (Docker Compose)

> [!NOTE]
> Для удобства файл файл `example.config.env` намеренно содержит полностью настроенные и готовые к работе переменные окружения.

Вся система — включая приложение, базу данных и автоматический накат миграций — поднимается одной командой.

```bash
docker compose up --build
```
Миграции Goose применятся автоматически, как только контейнер базы данных сообщит о готовности (`healthy`).

### 📡 Спецификация API
#### 1. Создание кошелька
Создает новый кошелек с дефолтным балансом 0.00.

* **URL**: `/api/v1/wallet`
* **Метод**: `POST`
* **Ответ (201 Created):**
```json
{
  "id": "eb7dc3a2-ff82-4c83-98d7-4431ee9ac0ab",
}
```

#### 2. Проведение транзакции
Выполняет атомарную операцию изменения баланса.
* **URL**: `/api/v1/wallet`
* **Метод**: `POST`
* **Тело запроса:**
```json
{
  "id": "eb7dc3a2-ff82-4c83-98d7-4431ee9ac0ab",
  "operationType": "DEPOSIT",
  "amount": 1000.50
}
```
(Допустимые типы операций: `DEPOSIT`, `WITHDRAW`)
* **Ответ (200 OK)**

#### 3. Получение баланса кошелька
Возвращает актуальный агрегированный баланс.
* **URL**: `/api/v1/wallet/:id`
* **Метод**: `GET`
* **Ответ (200 OK):**
```json
{
  "balance": 1000.50
}
```
